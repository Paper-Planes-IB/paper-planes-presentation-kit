# Paper Planes Presentation Kit

Собирать материал по единому производственному маршруту Paper Planes. Канонический upstream: `Paper-Planes-IB/paper-planes-presentation-kit`.

## Обязательный маршрут

1. Найти источники, ограничения и адрес конечного артефакта.
2. Создать один авторитетный содержательный `.md` до верстки.
3. Зафиксировать управленческую историю: ситуация, осложнение, вопрос, ответ.
4. Для каждого экрана указать заголовок-вывод, тезис, доказательства, источник с локатором, тип визуала и ожидаемое решение читателя.
5. Выбрать носитель по `references/carrier-router.md`.
6. Материализовать `.md` в HTML, PP Pages, PPTX, PDF или другой согласованный формат.
7. Проверить весь реальный рендер, затем прогнать текстового и слайдового критиков.
8. После правок пересобрать затронутые экраны и повторить полную проверку.

Нельзя начинать работу с декоративной верстки. Содержание, факты и логика должны быть готовы в `.md`.

## Структура содержательного Markdown

В начале зафиксировать:

- проект, аудиторию, автора, дату и версию;
- решение, которое поддерживает материал;
- основной источник данных;
- ограничения и неизвестные;
- ситуацию, осложнение, вопрос и ответ.

Для каждого экрана заполнить:

- `slide_id`;
- роль в истории;
- заголовок-вывод;
- тезис;
- факты и цифры;
- источник и точный локатор;
- интерпретацию;
- ограничение или пробел данных;
- тип визуала;
- решение или действие читателя;
- статус готовности.

Использовать шаблон канонического репозитория `templates/deck-content-template.md`.

## Выбор визуала

Форма следует за задачей:

| Задача | Подходящая конструкция |
|---|---|
| Сравнить варианты | таблица, матрица, профиль вариантов |
| Показать причинность | дерево причин, схема механизма, драйверная модель |
| Показать маршрут | процесс, дорожная карта, временная шкала |
| Показать решение | дерево решений, таблица условий, сценарная матрица |
| Показать организацию | оргмодель, RASCI, карта интерфейсов |
| Показать динамику | график, водопад, когортный вид |
| Показать доказательство | график, таблица, карта проблем, evidence map |

Не растягивать один карточный шаблон на весь материал. Один силуэт допустим максимум на двух последовательных содержательных экранах без отдельного обоснования.

## Визуальный канон

Использовать палитру:

| Роль | HEX |
|---|---|
| Основной текст | `#181D27` |
| Вторичный текст | `#414651` |
| Служебный текст | `#717680` |
| Линии | `#D5D7DA` |
| Мягкий фон | `#F7F8FA` |
| Второй мягкий фон | `#EEF1F5` |
| Фон страницы | `#F5F5F5` |
| Фон слайда | `#FFFFFF` |
| Главный акцент | `#FF5850` |
| Мягкий акцент | `#FFEBEA` |
| Подтвержденное состояние | `#EEF7EC` |
| Зона внимания | `#FFF5D8` |
| Информационный блок | `#E6EEF2` |

Белый остается основным фоном слайда. Коралл отмечает один главный акцент. Дополнительный цвет получает постоянное смысловое значение на всем материале.

Для HTML и слайдов использовать строгий формат 16:9: `1600 x 900` или `1280 x 720`. Минимальный текст в PowerPoint — 10 pt. Логотип, номер, поля и служебные зоны задавать глобально.

## Специализированные исполнители

- `pp-slidument` — плотный аналитический слайдумент, HTML-дека и PP Pages.
- `presentations` — чтение и нативная сборка PowerPoint.
- `pp-print-a4` — печатный A4 и PDF.
- `pp-interview-slides` — слайды по интервью.
- `pp-survey-slides`, `pp-survey-dashboard`, `pp-hr-survey-dashboard` — опросы и панели.
- `commercial-proposal-generator` — коммерческое предложение.
- `pp-text-critic` — обязательная редактура клиентского текста.
- `pp-slide-critic` или `presentation-qa` — обязательная проверка слайдов.

Этот скилл задает общий канон и маршрут. Производство выполнять профильным скиллом, сохраняя требования Presentation Kit.

## Приемка

Перед передачей пройти `references/acceptance-checklist.md`.

Обязательные доказательства готовности:

- актуальный `.md` с источниками;
- история читается по заголовкам;
- тип каждого визуала обоснован задачей;
- полный контактный лист или эквивалентный обзор всех экранов;
- проверка переполнения, обрезки и случайных пустот;
- отчет текстового критика;
- отчет слайдового критика;
- повторный рендер после исправлений;
- проверка итогового файла или публичного маршрута в целевом просмотрщике.

HTTP-ответ, успешная генерация файла или отсутствие ошибок сборщика не заменяют визуальную приемку.

## Версия и обновление

Перед новой крупной работой сверить HEAD канонического репозитория. Зафиксировать commit SHA в приемочной квитанции. Если локальный пакет отстает, обновить ссылки и правила до начала производства.

Текущий сведенный snapshot описан в `references/source-snapshot.md`. Проверочные сценарии находятся в `references/eval-cases.md`, результат проверки — в `references/eval-report.md`.
