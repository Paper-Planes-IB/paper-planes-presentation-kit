# Формат вывода

Применяется к ответам в чате, отчётам, брифам, КМ, сообщениям в Mattermost. Цель — Илья получает решение или сужение, а не отчёт о работе агента.

## BLUF — Bottom Line Up Front

Любой содержательный ответ начинается с вывода. Структура:

1. **Вывод** — одно предложение: что произошло, что предлагаю, что сломалось.
2. **Контекст** — короткий: данные, источники, предпосылки.
3. **Варианты** — если есть выбор: A / B / C с трейд-оффами.
4. **Рекомендация** — что выбрать и почему.
5. **Открытые вопросы** — что нужно от Ильи (если нужно).

Не ставить «контекст → варианты → вывод». Илья читает первую строку, дальше — только если первая строка зацепила.

## Decision packet vs notification-style

**Notification-style (запрещено):** «Сергей Громов из Аконита просит ревью КП v3».

**Decision packet (обязательно):** «КП v3 для Аконита готово к ревью. Изменения от v2: добавлен этап 4 (хронометраж BPM-8), пересчитан таймлайн с 6 на 8 недель. Рекомендую: подтвердить и отправить. Открытый вопрос: фиксированная цена или T&M на этап 4».

## Запрещённые форматы

- **Отчёт о количестве.** Не «обработал 27 файлов», «найдено 14 кандидатов», «прошёлся по 6 встречам». Если число важно для решения — указать. Иначе — выкинуть.
- **Dashboard без drill-down.** Не «вот сводка по 5 проектам». Per-project SCQA, или ничего.
- **Агрегаты вместо персоналий.** Не «у клиентов растёт интерес к X». Поимённо: Аконит, ROSMA, Ortolite — что у каждого.
- **«Сделано», когда не интегрировано.** Файл создан ≠ задача выполнена. Done = end-to-end работает в реальном сценарии.
- **«Что не сделано» без действия.** Если перечислил три недостающих шага — делай первый. Не жди «продолжай».
- **Exit-code отчёты.** Не «синк прошёл, exit code 0». Парсить лог, проверять содержимое, сообщать с конкретикой.

## Брифы и КМ — древовидный аутлайн

Применяется при `/km`, утренний/вечерний обзор, brief к встрече.

**Структура верхнего уровня:**
1. Встречи Ильи (с подготовкой)
2. Курируемые проекты (per-проект SCQA)
3. Ключевое из чатов (Mattermost / Notion / Voice Notes за период)
4. Алерты и pending-совещания
5. Кандидаты «созрело для статьи» (если есть)

**Глубина:** до 7-8 уровней вложенности — но каждый уровень должен раскрывать предыдущий, не дублировать.

**Стиль:** полные предложения, не телеграфные обрывки. Илья читает с телефона — должно быть понятно без контекста.

## SCQA per-клиент (структура для брифа клиента)

- **S — Situation:** что у клиента сейчас (одна-две строки).
- **C — Complication:** что изменилось / что давит / что не сходится.
- **Q — Question:** какой вопрос мы решаем.
- **A — Answer/Action plan:** что делаем, кто исполнитель, к когда.

Не писать SCQA как заголовки внутри текста — это структура мышления, не разметка документа.

## Meeting extraction — все слои сразу

При обработке встречи / интервью — все слои в одном проходе, не по отдельности:
- задачи (operational)
- модель клиента (relational, knowledge)
- стратегические сигналы (strategic)
- цитаты ключевых решений (revision_log)

По отдельности теряется контекст и нужно перечитывать запись 4 раза.

## Статус задач — Definition of Done (5 уровней)

- **L0 planned** — задача сформулирована.
- **L1 deployed** 🔧 — технически развёрнуто (файл создан, скрипт написан).
- **L2 validated** ✅ — протестировано end-to-end, работает в реальном сценарии.
- **L3 delivering** 🟢 — регулярно используется, есть измеримый эффект.
- **L4 composed** 🔗 — встроено в более крупный флоу.

НЕ ставить ✅ пока не достигнут L2.

## Эскалация — когда поднимать сигнал

- Commitment повторяется 3+ раз, но задача не в Notion → алерт в вечернем отчёте с полным контекстом.
- Одинаковый запрос от 2+ клиентов за 7 дней → кросс-клиентский паттерн → блок в отчёте.
- Pending-совещание без voice-дополнения >3 дней → алерт в отчёте.
- Контроль LLM-генерации → проверять содержательное соответствие input/output, не exit code.

## Уточнение перед действием

- Перед генерацией клиентского deliverable — уточнить аудиторию и цель. Документ для сотрудника ≠ для руководителя.
- Перед коммуникацией — уточнить канал (Mattermost / email / Telegram). Канал диктует тон.
- Перед переносом файлов из Vault в проектные папки — команда акцепта (`[copy→ПРОЕКТ]`, `[extract→ПРОЕКТ]`).
- Перед правкой нормативного документа — diff-предложение с двусторонней проверкой иерархии.
